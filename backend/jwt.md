## 웹의 상태 관리 변천사 (HTTP -> Cookie -> Session -> JWT)

1. HTTP
    - 당시 목적은 문서 전달
    - 요청 -> 응답 -> 연결 종료
    - 비연결, 무상태, stateless 프로토콜이라고 불림

2. 웹의 진화
    - 단순 문서가 아닌 애플리케이션으로 진화
    - 무상태 HTTP의 단점은 맥락이 없다는 것
        - 초기엔 서버 입장에서 상관없었지만, 점점 맥락을 필요로 하는 요구사항이 생김 ex) 장바구니

3. URL 기반 상태 전달
    - ex) http://shop.com/car?user_id=kim 처럼 URL에 정보를 추가하는 방식
    - 단점
        - 보안 대참사, URL만 봐도 민감 정보가 그대로 노출됨
        - 링크 공유 시 타인 계정으로 접속됨
        - 개발자가 모든 링크에 사용자 ID를 직접 넣어줘야 하는 번거로움

4. 쿠키의 등장
    - 장바구니 구현을 위해 고안
    - 상태를 서버가 아닌 클라이언트에 저장하자
    - 원리
        - 서버가 쿠키를 내려주면, 브라우저가 저장하고, 요청 시 쿠키를 자동으로 헤더에 포함해 전송
    - 한계
        - 보안 취약점
            - 클라이언트 저장 값이라 사용자가 임의로 값 수정 가능
            - XSS: 자바스크립트로 쿠키 탈취 가능
            - CSRF: 자동 전송되는 특성을 악용한 공격
        - 네트워크 부하
            - 매 요청마다 헤더에 포함되어 전송
            - 불필요한 트래픽 낭비 발생

5. 세션의 등장
    - 클라이언트는 못 믿으니 서버에 기억하자
    - 서버가 세션 아이디를 만들고, 그걸 기반으로 통신
    - 세션 ID는 아무 정보도 담지 않은 랜덤 문자열이고, 쿠키는 이 ID를 운반하는 역할만 수행
    - 한계
        - 서버 확장성 문제
            - 서버가 늘어나면 정합성 문제 발생 ex) sticky session, Redis Clustering 등등 -> 인프라 복잡도 증가
        - 서버 메모리 부담
            - 트래픽이 증가함에 따라 세션 객체도 같이 증가

6. JWT의 등장
    - 다시 무상태성으로 복귀
    - 토큰 자체에 필요한 정보가 담겨 있어 DB 조회 없이 토큰만으로 인증 가능
    - 쿠키를 잘 쓰지 않는 모바일이나 서버가 여러 대인 MSA 환경에서 표준처럼 사용
    - JWT 구조
        - Header: 알고리즘 정보
        - Payload: 데이터(ID, Role, Exp)
        - Signature: 위변조 방지 서명
    - 한계
        - payload의 크기: 정보가 많을수록 토큰이 길어지고 네트워크 낭비
        - 강제 만료 불가: 한 번 발급된 토큰은 유효기간까지 서버 제어 불가능 + 탈취 시 만료기간까지 계속 악용 가능
        - 해결책: Refresh Token, Blacklist

7. 결론
    - 보안이 중요하다? 세션이 적합할 수도
    - 확장성이 중요하다? JWT가 유리

## JWT가 탈취 당한다면?

1. JWT는 데이터 노출을 책임지지 않는다
    - JWT 보장 O: 출처, 위조방지, 무결성
    - JWT 보장 X: 기밀성, 암호화

2. 누구나 볼 수 있는 payload
    - Header + Payload + Signature 각각을 Base64URL로 인코딩해 이어붙인 것일 뿐 암호화가 아님. 즉, 누구나 디코딩 가능
    - 따라서 숨겨야 할 정보가 아니라 읽을 수 있지만 바꾸면 안 되는 정보만 담아야 함

3. Token Hijacking = 토큰 탈취
    - 토큰만 가지고 있으면 그대로 요청에 사용해 사용자로 위장 가능
    - 시나리오
        1. 탈취
            - XSS 공격
            - 로그 노출
            - 공용 PC 등
        2. 공격
            - 별도의 토큰 수정 없이 헤더에 그대로 붙여넣어 사용 가능
        3. 서버
            - 서버는 서명을 확인하고, 만료 전이라면 정상 유저라고 판단

4. 대처법
    - 민감한 정보는 payload에서 제외
    - XSS 방어
    - HTTPS 사용
    - Access Token 수명은 짧게 가져가되 Refresh Token 활용

## 어떻게 방어할 수 있는가?

1. JWT 본질과 보안 철학
    - 무상태
    - Bearer Token
    - 기본 원칙은 민감한 정보는 포함하면 안 된다

2. 실무에선 어떻게 막아야 하는가?
    - 훔치지 못하게 하기
        - HTTPS 사용 필수
        - XSS 방어는 로컬 스토리지가 아닌 HttpOnly Cookie로
            - 또한 쿠키 사용 시 SameSite=Lax 또는 Strict 설정 필수 (for CSRF)
        - 로그 마스킹 (서버 로그에 Authorization 헤더 기록 금지)
    - 훔쳐가도 쓸모없게 하기
        - 유효기간 단축
            - Access Token: 30분 내외로 탈취돼도 곧 만료
            - Refresh Token: 2주 정도로 사용자 편의성 유지
        - 환경 검증
            - 토큰 안에 User-Agent 해시값을 포함하는 등의 방법으로 발급 당시 환경과 다르면 차단 (보조)
        - RTR (Refresh Token Rotation)
            - 토큰 갱신 시 Refresh Token도 무조건 교체
            - 토큰 재사용이 감지되면 해당 유저의 모든 토큰 즉시 무효화 및 강제 로그아웃
        - 중요 기능 보호 & 서버 제어
            - 계좌 이체, 비밀번호 변경 등은 2차 인증 필수
            - 블랙리스트 관리(Redis): 로그아웃 시 토큰 고유 ID인 jti를 저장하여 차단

3. 실무 구현 전략
    - 순수 Stateless
        - 방식: AT는 짧고, RT는 길게
        - 보완: 토큰 내 User-Agent 정보 포함
        - 장점: 무상태 -> 확장성, 서버 저장 X, DB 조회 없음
        - 단점: 토큰 탈취 시 제어 불가능
    - 하이브리드
        - 방식: AT는 짧게 + RT는 서버 관리
        - 장점: 탈취 시 즉시 무효화 가능 -> RTR 및 Reuse Detection
        - 단점: stateful
