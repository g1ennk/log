# 1. CS/지식형

"REST가 뭔가요", "GC는 어떻게 동작하나요" 같은, 개념 자체를 설명하라는 질문.

## 포맷

정의 → 원리 → 예시 → 장단점 → 실무

순서대로 다 말하면 길어지니까, 실전에서는 정의랑 원리까지만 20~30초 정도로 짧게 말하고 끝을 살짝 열어둔다. 그럼 면접관이 "예를 들면요?" 같은 질문을 자연스럽게 하게 되고, 그때 예시/장단점/실무를 하나씩 꺼낸다.

글은 줄글이 아니라 아래처럼 라벨을 달아서 쓴다. 이렇게 쪼개서 써봐야 발화할 때도 구조가 자연스럽게 떠오른다.

## 예시 — "REST에 대해서 설명해주세요"

- 정의: REST는 자원을 URI로 표현하고 HTTP 메서드로 자원의 상태를 주고받는 아키텍처 스타일이다.
- 원리: 핵심은 클라이언트-서버 분리, 무상태성, 캐시 가능성, 일관된 인터페이스 같은 제약조건을 지키는 것이고, 이걸 지켜야 RESTful하다고 할 수 있다.
- 예시: `/users/1`은 특정 사용자 자원, GET은 조회, POST는 생성, PUT/PATCH는 수정, DELETE는 삭제.
- 장단점: 구조가 일관되고 결합도가 낮아지지만, URI·메서드만 쓴다고 REST가 되는 건 아니라서 무상태성 같은 제약도 지켜야 한다.
- 실무: 제약을 다 엄격히 지키기보단 요구사항에 맞춰 RESTful하게 설계하는 경우가 많다.

발화할 땐 정의·원리까지만 먼저 말하고 멈춘다. 그럼 보통 "예를 들면요?" 같은 꼬리질문이 들어오고, 그때 예시/장단점/실무를 순서대로 꺼낸다.

## 글 구조

CS 노트는 파일 하나를 이 세 파트로 쓴다.

1. **요약** — 위 포맷(정의 → 원리 → 예시 → 장단점 → 실무)을 라벨로 압축해서 정리
2. **개념** — 배경과 원리를 근거·비교·수치까지 상세히 풀어 쓴 설명
3. **예상 질문** — 실제로 나올 법한 꼬리질문과 답변을 미리 정리
