# system-design

"URL 단축기 설계해보세요" 같은 질문. 신입 면접에도 가볍게 나오는 편이다.

## 포맷

문제 이해 → 요구사항 확인 → 불변식 정의 → 개략 설계 → 상세화 → 복구·관측성 → 테스트 → 트레이드오프

요구사항 확인은 **내가 면접관에게 질문하는** 단계다. 이후에는 확정된 요구사항과 불변식을 기준으로 설계하고, 면접관의 반박에 답한다.

설계로 끝내지 않고 스펙 문서와 구현까지 이어간다 — 스펙과 코드는 `~/projects/sd-practice/<slug>`에 둔다.

## 진행 규칙

1. 문제 문서의 빈칸을 먼저 채운다. 구현이나 기존 제출물은 보지 않는다.
2. 요구사항이 모호하면 임의로 숨기지 않고 `가정`으로 명시한다.
3. 정상 흐름보다 먼저 절대 깨지면 안 되는 불변식을 적는다.
4. 받은 반박과 처음 설계를 바꾼 이유까지 기록한 뒤 구현으로 넘어간다.

## 질문 축

요구사항 확인 단계에서 던질 질문의 정본. 문제가 바뀌어도 축은 그대로다 — 외울 건 개별 질문이 아니라 이 순서다.

- **범위** — 어떤 기능이 필수인가, 이번에 안 다뤄도 되는 건 무엇인가
- **규모** — 사용자·요청·데이터가 얼마나 되는가, 피크와 평균의 차이는
- **정합성** — 틀리면 안 되는 것은 무엇인가, 잠깐 어긋나도 되는 것은
- **지연** — 어디까지 실시간이어야 하는가
- **제약** — 기존 시스템·팀·기한 중 설계를 묶는 것이 있는가

## 완료 기준

- 요구사항의 가정과 범위 밖 항목이 분리되어 있다.
- 핵심 불변식마다 이를 지키는 설계 장치와 실패 테스트가 연결된다.
- 정상·중복·동시성·부분 실패·재시작 시나리오를 설명할 수 있다.
- API, 데이터 모델, 트랜잭션 경계가 서로 모순되지 않는다.
- 선택한 설계와 버린 대안의 조건·비용을 설명할 수 있다.
- 구현 테스트가 설계 문서의 핵심 시나리오를 검증한다.
