# 왜 코루틴 방식이 기존 스레드 방식보다 가벼운지 설명해주세요.

## 1. 요약

### 1.1. 정의

- 코루틴은 스레드를 새로 만들지 않고 기존 스레드 위에서 동작하는, 훨씬 가벼운 논리적 실행 단위다.

### 1.2. 원리

- 스레드 생성은 OS에 커널 자원을 요청해야 하지만 코루틴은 객체 하나 만드는 수준의 비용만 든다.
- 전환도 커널 모드 진입 없이 user space에서 실행 지점과 로컬 변수만 저장하며,
- I/O처럼 대기가 필요한 지점(`suspend`)에서는 점유하던 스레드를 반납해 다른 코루틴이 즉시 쓸 수 있게 한다.

### 1.3. 예시

- 스레드 1,000개를 만들면 약 1GB 메모리가 필요하지만, 코루틴 1,000개는 몇 MB면 충분하다.
- Java 21의 Virtual Thread도 같은 문제의식으로 나온 개념이다.

### 1.4. 장단점

- 메모리 및 컨텍스트 스위칭 비용이 작아 I/O 바운드 동시 작업을 대량으로 처리하기엔 유리하지만,
    - 예외가 여러 코루틴에 걸쳐 전파되므로 에러 처리 범위를 구조적으로 설계해야 하는 부담도 있다.
- CPU 연산이 중심인 작업에서는 스레드 풀이 더 단순하고 예측 가능하다.

### 1.5. 실무

- I/O가 많은 서버는 코루틴(Java라면 Virtual Thread)으로 스레드 자원을 아끼고,
- CPU 바운드 작업이거나 복잡한 비동기 조합이 필요하면 스레드 풀, CompletableFuture를 쓰는 식으로 상황에 맞춰 고른다.

## 2. 개념

### 2-1. 배경

- 서버가 동시에 처리해야 하는 요청 수가 늘어나면서, 요청마다 스레드를 하나씩 할당하는 전통 방식은 한계에 다달았다.
    - 스레드는 생성 비용이 크고 각 스레드가 기본적으로 1MB 안팎의 스택 메모리를 점유한다.
    - 따라서 수천 개의 동시 요청을 스레드로 감당하려면 메모리와 컨텍스트 스위칭 비용이 폭증한다.
- 이러한 문제를 해결하기 위해 등장한 것이 스레드보다 훨씬 가벼운 실행 단위인 `코루틴`이다.
    - 코루틴은 Kotlin 생태계를 중심으로 서버 애플리케이션의 동시성 처리 방식으로 널리 자리 잡았다.

### 2-2. 메모리와 생성 비용 차이

- 코루틴은 별도의 스레드를 새로 만드는 대신 이미 존재하는 스레드 위에서 실행하는 논리적 작업 단위이다.
    - 스레드 생성 시 OS에 시스템 호출로 커널 수준의 자원을 할당받아야 한다.
    - 반면에 코루틴은 단순한 객체를 하나 생성하는 것과 비슷한 수준의 비용만 발생한다.
- 결과적으로 스레드 1000개 생성 시 1GB 메모리가 필요하다면, 코루틴은 몇 MB 수준의 메모리만으로 충분하다.

### 2-3. 컨텍스트 스위칭 경로

- 전환 비용의 차이는 전환이 일어나는 위치에서 비롯된다.
    - 스레드 간 전환은, OS 커널이 개입해 레지스터와 메모리 맵 같은 실행 상태를 저장하고 복원해야 하므로 비용이 크다.
        - 스레드 A 실행 -> 커널 모드 진입 -> 레지스터, 스택 저장 및 복원 -> 스레드 B 실행
    - 반면 코루틴 간 전환은 커널 개입 없이 애플케이션이 실행되는 user space 안에서 이루어진다.
        - 또한 실행 지점과 로컬 변수 상태만 heap에 저장하면 되므로 훨씬 가볍다.
        - 코루틴 A 실행 -> user space 상태 저장 -> 코루틴 B 실행
- 주의할 점은 코루틴은 스레드를 대체하는 개념이 아닌 스레드 위에서 동작하는 더 작은 실행 단위라는 점이다.
    - 결국 코루틴도 어느 시점엔 실제 스레드에서 실행되어야 한다.
    - 다만 그 스레드를 블로킹하지 않고 여러 코루틴이 나눠쓴다는 점이 핵심이다.

### 2-4. 일시 중단과 스케줄링

- 코루틴은 I/O처럼 시간이 걸리는 작업을 만나면 `suspend` 지점에서 실행을 멈추고 자신이 점유하던 스레드를 반납한다.
    - 이로 인해 해당 스레드는 대기 중인 다른 코루틴을 실행하는 데 즉시 재사용될 수 있고,
    - 원래 작업은 결과가 준비되는 시점에 다시 스케줄링 되어 재개된다.
- 이러한 방식 덕분에 스레드는 항상 실제로 계산이 필요한 작업에만 쓰이고, 소수의 스레드로 수천 개의 코루틴을 돌릴 수 있다.

### 2-5. Java Virtual Thread와의 비교

- Java 21부터는 JVM 차원에서 유사한 목표를 가진 Virtual Thread가 도입되었다.
    - VT도 커널 스레드보다 훨씬 가볍고 블로킹 작업에서 캐리어 스레드를 자동으로 반납한다는 점에서 코루틴과 유사하다.
    - 단, 개발자가 디스패처를 관리할 필요 없이 JVM이 알아서 처리해 기존 블로킹 코드를 그대로 사용할 수 있다는 차이가 있다.
- 실측 비교에서는 VT가 코루틴보다 다소 빠르고 메모리 효율도 높게 나타났다.
    - 단, Kotlin 환경 혹은 코루틴 환경이라면 여전히 코루틴이 합리적인 선택이다.

## 3. 예상 질문

### 3-1. Java의 VT와 Kotlin의 Coroutine은 동시성 처리 방식에서 어떻게 다른가?

- VT는 JVM이 스케줄링과 캐리어 스레드 반납을 자동으로 처리해 기존 코드를 거의 그대로 사용 가능하다.
- Coroutine은 개발자가 직접 디스패처와 실행 컨텍스트를 명시적으로 구성해야 함. (세밀한 제어 가능)
- 실측 성능은 VT가 근소하게 앞서지만 큰 차이는 없다.

### 3-2. 전통 스레드 풀과 코루틴 중 어떤 상황에서 코루틴을 선택해야 하나?

- 코루틴: 대기 중 스레드 반납 -> 많은 동시 작업 처리 가능
    - 많은 수의 I/O 바운드 작업을 동시에 처리 필요한 경우
    - 각 작업이 자주 대기 상태에 빠지는 경우
- 스레드 풀 방식: 스레드 수 제한 -> 대기 작업 증가 -> 풀 고갈
    - CPU 연산이 중심인 작업인 경우 스레드 풀 방식이 더 단순하고 예측 가능하다.

### 3-3. 동기 블로킹 처리와 코루틴 기반 비동기 처리의 에러 처리 방식은 어떻게 다른가요?

- 동기 블로킹 처리
    - 예외가 호출 스택에 따라 그대로 전파되므로 try-catch로 직관적인 처리 가능
- 코루틴 기반 비동기 처리
    - 작업이 여러 코루틴에 걸쳐 실행됨
    - 따라서 하나의 코루틴에서 발생한 예외가 상위로 전파되는 범위와 시점을 구조적으로 설계해야 함.

### 3-4. CompletableFuture와 Virtual Thread 중 어떤 상황에서 Virtual Thread를 선택하나?

- CompletableFuture
    - 여러 비동기 작업을 조합하거나 파이프라인을 구성하는 데 강점
    - 단, 콜백 중첩으로 가독성이 떨어질 수 있음
- Virtual Thread
    - 콜백 체이닝 없이 기존의 블로킹 스타일 코드를 그대로 유지하면서 동시성을 높이고 싶을 때
- 결론
    - 단순 요청-응답 구조의 대량 동시성 처리 -> Virtual Thread
    - 복잡한 비동기 조합 로직 -> CompletableFuture

### 3-5. 스레드 풀과 코루틴 디스패처의 스케줄링 방식은 어떻게 다른가?

- 스레드 풀
    - OS 스케줄러가 제한된 수의 스레드를 선점형으로 스케줄링
    - 스레드 블로킹 시 해당 스레드 자체가 멈춤
- 코루틴 디스패처
    - 소수의 스레드 위에서 다수의 코루틴을 협력적으로 스케줄링
    - 코루틴 중단 시 즉시 다른 코루틴에 스레드를 넘겨줌
- 이 차이로 같은 스레드 수로도 코루틴 방식이 훨씬 많은 동시 작업 소화 가능
