# 왜 코루틴 방식이 기존 스레드 방식보다 가벼운지 설명해주세요.

## 1. 요약

### 1.1. 결론

- 코루틴이 스레드보다 가벼운 이유는 커널 개입 없이 user space에서 생성·전환되기 때문이다.

### 1.2. 왜

- 서버가 동시에 처리할 요청이 늘면서, 요청마다 스레드를 하나씩 쓰는 전통 방식은 스레드 생성 비용과 스레드당 약 1MB의 스택 메모리 때문에 한계에 부딪혔다. 스레드보다 훨씬 가벼운 실행 단위가 필요해서 코루틴이 등장했다.

### 1.3. 원리

- 스레드 생성은 OS에 커널 자원을 요청해야 하지만 코루틴은 객체 하나 만드는 수준의 비용만 든다.
- 전환도 커널 모드 진입 없이 user space에서 실행 지점과 로컬 변수만 저장하며, I/O처럼 대기가 필요한 지점(`suspend`)에서는 점유하던 스레드를 반납해 다른 코루틴이 즉시 쓸 수 있게 한다.
- 그 결과 스레드 1,000개는 약 1GB 메모리가 필요하지만 코루틴 1,000개는 몇 MB면 충분하다. Java 21의 Virtual Thread도 같은 문제의식으로 나온 개념이다.

### 1.4. 판단 기준

- 메모리·컨텍스트 스위칭 비용이 작아 I/O 바운드 동시 작업을 대량으로 처리하기엔 유리하지만, 예외가 여러 코루틴에 걸쳐 전파돼 에러 처리 범위를 구조적으로 설계해야 하는 부담이 있다.
- CPU 연산이 중심인 작업에서는 스레드 풀이 더 단순하고 예측 가능하다 — I/O가 많은 서버는 코루틴(Java라면 Virtual Thread)으로 스레드 자원을 아끼고, CPU 바운드거나 복잡한 비동기 조합이 필요하면 스레드 풀·CompletableFuture를 쓴다.
