# JVM의 장단점

## 1. 요약

### 1.1. 결론

JVM은 자바 바이트코드를 해석 및 실행하는 런타임으로, 플랫폼에 상관없이 같은 코드를 실행할 수 있게 해주는 것이 가장 큰 장점입니다.

### 1.2. 장점

C/C++은 소스를 미리 네이티브 코드로 컴파일하지만, 자바는 클래스 파일만 배포하고 JVM이 이를 해석해 실행하므로 "Write Once, Run Anywhere"가 적용됩니다. 이 위에서 GC 기반 자동 메모리 관리, 바이트 검증 보안, 인터프리터와 JIT의 런타임 최적화 장점까지 존재합니다.

### 1.3. 단점

하지만 클래스 로딩, 검증, JIT 워밍업 등 언급한 모든 장점이 오버헤드로 돌아와 초기 실행 속도가 네이티브 언어보다 느리고, GC가 동작하는 동안 애플리케이션 스레드가 멈추는 Stop-The-World 지연도 대표적인 단점입니다.

### 1.4. 실무

따라서 실무에서는 Spring Boot 배포 시 워밍업 특성을 고려해 헬스체크 통과 후 트래픽을 점진적으로 늘리는 방식으로 초기 지연을 완화합니다.

## 2. 꼬리 질문

### 2.1. 자바와 C/C++의 실행 방식 차이가 실행 속도에 어떤 영향을 주는가?

C/C++은 컴파일 시점에 이미 CPU 아키텍처에 맞는 네이티브 코드로 변환되므로 실행 즉시 최고 속도를 낼 수 있습니다.

반면 자바는 플랫폼 독립적인 바이트코드로 변환되고, 이를 JVM이 해석하고 컴파일하는 과정을 거쳐 초기에는 오버헤드가 발생합니다.

### 2.2. 인터프리터 방식과 JIT 컴파일 방식의 차이

인터프리터는 바이트코드를 한 줄씩 읽어 그때그때 해석해 실행하므로 시작은 빠르지만 같은 코드를 반복 실행할 때마다 매번 해석 비용이 들어갑니다.

JIT는 자주 호출되는 코드를 감지해 이를 네이티브 코드로 변환해 캐시해두므로, 이후 호출부터는 네이티브 속도로 실행되지만, 컴파일 자체에 시간과 메모리가 들기 때문에 한 번 실행되는 코드에는 오히려 손해일 수 있습니다.

따라서 JVM은 둘 중 하나를 선택하는 것이 아니라 두 방식을 함께 사용해 시작 속도와 처리량을 모두 확보합니다.

### 2.3. JIT 컴파일러가 "자주 사용되는 코드"를 어떻게 판단하는가

우선 당연히 실행 빈도가 높은 코드를 우선 컴파일 대상으로 선택합니다. 한 번 실행되는 코드까지 컴파일 시 컴파일 비용이 실행으로 얻는 이득보다 커질 수 있기 때문입니다.

따라서 JVM은 메서드 호출 횟수와 반복문 실행 횟수를 계속 추적하다 일정 임계치를 넘으면 해당 코드를 컴파일 대상으로 올려 실제 실행 통계에 기반해 최적화 대상을 선별하는 것이 정적 컴파일과 구분되는 지점입니다.

### 2.4. JIT 캐시가 꽉 차면?

캐시가 여유가 있을 땐 자주 실행되는 코드를 계속해서 감지하며 컴파일하고 저장하여 실행 성능이 점진적으로 개선됩니다.

하지만 캐시가 가득 차면 더 이상 새로운 코드를 컴파일 해 저장할 공간이 없으므로 hot코드가 계속 인터프리터로 실행되고 이는 결국 시간이 지나도 성능이 기대만큼 올라오지 않아 정체 현상이 나타날 수 있습니다.

실무에선 이런 상황을 대비해 컴파일 캐시 공간을 실행 환경에 맞게 넉넉히 확보해두는 것이 중요합니다.

### 2.5. JVM 배포 시 초기 요청 응답 속도가 느린 이유

배포 직후에는 클래스 로더가 필요한 클래스를 아직 다 메모리에 적재하지 않은 상태라 첫 요청에서 클래스 로딩 자체가 지연 요인이 되고, 여기에 더해 장시간 떠 있는 서버 애플리케이션이 JIT의 이점을 훨씬 크게 얻습니다.

JIT는 실행 통계를 충분히 쌓아야 최적화가 진행되는데, 짧게 실행되고 끝나는 배치와 같은 작업은 통계가 쌓이기 전에 종료되어 컴파일에 이득을 거의 못 봅니다. 반대로 상시 트래픽을 받는 웹 서버는 시간이 지날수록 반복 호출되는 코드가 최적화되어 처리량이 안정적으로 올라갑니다.

단, 이러한 특성 때문에 최적화가 덜 된 상태인 초기에는 요청이 느릴 수 있기에 사전 워밍업으로 이를 보완하기도 합니다.
